## Simple Summary
A transaction pricing mechanism that includes fixed-per-block network fee that is burned and dynamically expands/contracts block sizes to deal with transient congestion.

## Abstract
There is a base fee per gas in protocol, which can move up or down by a maximum of 1/8 in each block. The base fee per gas is adjusted by the protocol to target an average gas usage per block instead of an absolute gas usage per block. The base fee is stored in the block header. The base fee per gas is burned. Transactions specify the maximum fee per gas they are willing to give to miners to incentivize them to include their transaction (aka "miner tip"). Transactions also specify the maximum fee per gas they are willing to pay in total (aka "max fee"), which covers both the base fee and the miner tip. The difference between the max fee and base fee + miner tip is refunded to the transaction sender.

## Motivation
The Ethereum gas market currently uses a simple auction mechanism, where users specify a gas price bid for miners to include their transactions. This leads to various inefficiencies:
* **Mismatch between volatility of transaction fee levels and social cost of transactions**: bids to include transactions on mature public blockchains, that have enough usage so that blocks are full, tend to be extremely volatile. On Ethereum, minimum bids typically spike up to tens or even hundreds of gwei (even going above 1000 gwei at times), despite the fact that the long-run competitive equilibrium cost of transactions is barely above 2 gwei.
* **Needless delays for users**: because of the hard per-block gas limit coupled with natural volatility in transaction volume, transactions often wait for dozens of blocks before being included, despite fee levels being sufficient to pay for inclusion.
* **Inefficient first-price gas price auction**: a user that values getting their transaction included makes an effective payment equal to their bid, regardless of what anyone else on the network is bidding. Traditional single-price auctions, where each transaction included in a block pays only the lowest bid that would have been sufficient to include all transactions that actually were included in a block, have significant game-theoretic efficiency advantages, and are easier for transaction senders to understand.
* **Instability of blockchains with no block reward**: in the long run, blockchains where there is no issuance (including Bitcoin and Zcash) at present intend to switch to rewarding miners primarily through transaction fees. However, there are known issues with this mechanism, both based on theoretical results from selfish mining research and the actual stability problems that have existed for years on Bitcoin forks that have low rewards (variance in rewards leads to a growing incentive to switch between chains). There is a large body of research on the instability of these fee markets.
* **Inefficient incentives for selfish mining strategies**: a miner at present is incentivized to include a transaction in a block because of its transaction fee. However, if there is a particularly high-fee transaction, then if the miner sees that transaction first, they would be incentivized to mine a (possibly empty) block first, and only then include the transaction in the next block.

This EIP proposes a way to address (2), (3), (4) and (5). It only partially addresses (1), though it does make the issue significantly less severe.

## Specification
### Parameters
| Constant | Value |
| - | - |
| `INITIAL_FORK_BLOCK_NUMBER` | TBD |
| `INITIAL_BASE_FEE` | 1000000000 |
| `BASE_FEE_MAX_CHANGE_DENOMINATOR` | 8 |
| `ELASTICITY_MULTIPLIER` | 2 |
| `MAX_EMPTY_BLOCKS` | 1 |

### New header fields
The values below are added to the header:
* `base_fee_per_gas`: 256-bit EVM word representing fee per gas in wei that all transactions in the block must at least pay

### New transaction fields
The values below replace `gas_price` field of the transaction:
* `max_fee_per_gas`: 256-bit EVM word representing maximum fee (inclusive of the base fee and miner tip) per gas in wei that can be charged to the sender (replaces the pre-1559 `gas_price` field)
* `max_priority_fee_per_gas`: 256-bit EVM word representing gas price in wei that goes to miner
* `gas_price` field of transaction receipt is base fee + min(max_priority_fee_per_gas, max_fee_per_gas - base_fee)

### Updated block validity
A block is valid if:
* For all transactions, `max_fee_per_gas` ≥ `base_fee_per_gas`
* `gas_used` ≤ `gas_limit`

### Gas accounting and refunds
Let `gas_price` = `base_fee_per_gas` + min(`max_priority_fee_per_gas`, `max_fee_per_gas` - `base_fee_per_gas`).

Transaction senders pay `gas_used` * `gas_price`. `gas_used` * `base_fee_per_gas` is burnt and `gas_used` * (`gas_price` - `base_fee_per_gas`) is given to the miner.

### Block size targeting
If a block is >= 50% full, then the base fee for the next block increases. If a block is < 50% full, then the base fee decreases.

Let `parent` be the parent block.

The formula for base_fee_per_gas calculation is:
```python
parent_gas_target = parent.gas_limit // ELASTICITY_MULTIPLIER
parent_gas_delta = parent.gas_used - parent_gas_target
parent_base_fee_per_gas = parent.base_fee_per_gas
parent_base_fee_per_gas * parent_gas_delta // parent_gas_target // BASE_FEE_MAX_CHANGE_DENOMINATOR
```

If the parent gas usage is the same as the target gas usage, the base fee is the same in the current block as in the parent block. If the parent block used more gas than its target, the base fee increases and decreases otherwise.

The formula is as follows:
```python
def calc_base_fee_per_gas(parent):
    parent_gas_target = parent.gas_limit // ELASTICITY_MULTIPLIER
    parent_base_fee_per_gas = parent.base_fee_per_gas
    if parent.gas_used == parent_gas_target:
        return parent_base_fee_per_gas
    elif parent.gas_used > parent_gas_target:
        gas_used_delta = parent.gas_used - parent_gas_target
        base_fee_per_gas_delta = max(parent_base_fee_per_gas * gas_used_delta // parent_gas_target // BASE_FEE_MAX_CHANGE_DENOMINATOR, 1)
        return parent_base_fee_per_gas + base_fee_per_gas_delta
    else:
        gas_used_delta = parent_gas_target - parent.gas_used
        base_fee_per_gas_delta = parent_base_fee_per_gas * gas_used_delta // parent_gas_target // BASE_FEE_MAX_CHANGE_DENOMINATOR
        return parent_base_fee_per_gas - base_fee_per_gas_delta
```

The `base_fee_per_gas` of the genesis block is `INITIAL_BASE_FEE`.

For blocks where `block.number >= INITIAL_FORK_BLOCK_NUMBER`, the base fee is set as above, regardless of the block's relation to the fork block. For example `calc_base_fee_per_gas(fork_block_parent)` is still used to calculate the base fee of the fork block, even though the parent is not EIP-1559.

When `block.number >= INITIAL_FORK_BLOCK_NUMBER`, if `block.number != INITIAL_FORK_BLOCK_NUMBER`, then `block.base_fee_per_gas` must not be null and must equal `calc_base_fee_per_gas(block.parent)`.

### Pre-EIP-1559 transaction compatibility
Pre-EIP-1559 transactions will continue to function as before. Users who are indifferent to how their fee is allocated can simply set `max_fee_per_gas = max_priority_fee_per_gas = gas_price`. The `gas_price` parameter in the transaction receipt will continue to be the effective gas price used for the transaction.

Pre-EIP-1559 transactions will appear with `max_fee_per_gas` = `max_priority_fee_per_gas` = `gas_price`.

### Transaction ordering
Let the "effective gas price" of a transaction be:
```python
min(transaction.max_priority_fee_per_gas, transaction.max_fee_per_gas - block.base_fee_per_gas) + block.base_fee_per_gas
```

Transactions can be sorted according to their effective gas price.

### Empty blocks and selfish mining
A miner could mine an empty block with just the coinbase transaction, and we would need to define what the parent gas delta is in such a case (because we divide by that value). The implementation here allows the empty blocks but caps the number of consecutive empty blocks to a max of 1.

To solve for the selfish mining case, we do require that if `block.number == parent.number + 1`, then `block.base_fee_per_gas >= parent.base_fee_per_gas` (i.e. there is no benefit to mining an empy block in the block immediately following a full block).

### Estimating gas price
In a post-EIP-1559 environment, there are two values users need to specify: `max_fee_per_gas` and `max_priority_fee_per_gas`. Wallets will need to calculate a suggested `max_fee_per_gas` value by taking into account the base fee and the tip.

The base fee can be obtained from the chain itself. The tip can be chosen according to a variety of fee market strategies.

### Optional base fee in header for blocks before EIP-1559
To make gas estimations easier for blocks before EIP-1559, we may consider adding a base fee in header for blocks before EIP-1559. This header field would not affect consensus.

Suggested formula:
```
parent_gas_target = parent.gas_limit // ELASTICITY_MULTIPLIER
parent_gas_delta = parent.gas_used - parent_gas_target
parent_base_fee_per_gas = parent.base_fee_per_gas
parent_base_fee_per_gas * parent_gas_delta // parent_gas_target // BASE_FEE_MAX_CHANGE_DENOMINATOR
```

For blocks before EIP-1559, the base fee would be available "as if" the block was an EIP-1559 block.

## Rationale
### Considerations for miners
Miners generally prefer the status quo, as any change to the fee market has the potential to disrupt their established revenue model and operational decision-making. Consensus does not exist on whether this EIP would lead to a net increase or decrease in miner extractable value.

### Base fee adjustment mechanism
The base fee adjustment mechanism is designed to increase/decrease (by a max of 12.5% per block) so that blocks are targeted at 50% full.

The base fee is sent to the burn address. First, this ensures that only ETH is used to pay for transactions on Ethereum, cementing the economic value of ETH in the Ethereum platform and reducing risks associated with miners extracting value from users. Second, it ensures that a portion of the transaction fee is burned.

The base fee is adjusted according to the level of congestion on the network. If blocks are more than 50% full, the base fee increases. If blocks are less than 50% full, the base fee decreases.

### Overflow safety
The formula for calculating base fees has a built-in overflow safety check. The common case for overflows is when a > 2^256. MAX_CHANGE_DENOMINATOR = 8, therefore for overflows to happen, the new base fee would need to increase by > 2^253 in a single block. The current ETH in circulation is ~ 2^88 wei. So even if there were 1000x more ETH (2^98 wei) and all of it were spent on a single block, the new base fee would be (2^98 * 2^98) = 2^196 which is still far lower than 2^253. So for all practical purposes, overflow is unlikely.

## Backwards Compatibility
Since this EIP proposal changes the core functionality of the Ethereum protocol, backwards compatibility concerns inevitably arise. Let's explore these in detail:

### Transaction Compatibility
EIP-1559 maintains backward compatibility with existing transactions by treating them as if they have the same `max_fee_per_gas` and `max_priority_fee_per_gas` values, both equal to the transaction's original `gas_price`. This means pre-EIP-1559 transactions will continue to work under the new fee market mechanism, though they won't benefit from the potential fee savings that the new transaction format offers.

### Client Compatibility
All Ethereum clients must implement this EIP to maintain consensus with the network after the fork block. Major client implementations like Geth, OpenEthereum, Nethermind, and Besu are expected to support this change.

### Smart Contract Compatibility
Smart contracts that rely on gas price mechanics may need to be updated to properly work with the new fee structure. Specifically:
- Contracts that use `tx.gasprice` for calculations will still work but will interpret it as `base_fee + priority_fee`
- Gas price oracle contracts will need to be updated to understand the new fee model
- Smart contracts that provide gas price suggestions may become obsolete or need updates

### Wallet and Infrastructure Compatibility
Wallets and infrastructure providers need to update their software to support the new transaction format with `max_fee_per_gas` and `max_priority_fee_per_gas` fields. Many wallets and providers implemented this during the months leading up to the London hard fork.

### Impact on External Systems
External systems that track or analyze Ethereum transactions will need to be updated to handle the new transaction format and fee mechanics.

## Security Considerations
### Miner Extractable Value (MEV)
EIP-1559 changes the incentive structure for miners. With a portion of gas fees being burned, miners' incentives shift more heavily towards extracting value via transaction ordering, potentially leading to increased MEV activity.

### Empty Block Attacks
To prevent selfish mining, this EIP includes a rule that addresses empty block attacks by requiring that if a block immediately follows its parent, its base fee must be at least equal to the parent's base fee. This prevents miners from mining empty blocks to manipulate the base fee downward.

### Base Fee Manipulation
While miners cannot directly manipulate the base fee, they could indirectly influence it by consistently filling blocks beyond the target capacity to drive up the base fee, or by including their own transactions to artificially reach the target capacity. However, these strategies have economic costs that disincentivize such behavior.

### Fee Spikes During High Congestion
The 12.5% maximum base fee adjustment per block means that fee levels can still spike dramatically during periods of extreme congestion. While this EIP reduces fee volatility compared to the first-price auction model, it doesn't eliminate it entirely.

### Chain Reorganization Considerations
In the case of chain reorganizations, the base fee calculation remains deterministic and doesn't introduce new consensus risks.
